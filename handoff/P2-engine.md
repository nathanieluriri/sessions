# P2. Scheduling and catalog engine (server)

Read first: `.gauntlet/BRIEF.md`, `.gauntlet/ARCHITECTURE.md`, then the code you will touch. The foundation commit already has: migrations 0005 and 0006, types for the new columns, `session_slots` repo method `catalogRepo.sessionSlots`, redaction, the producer role, and `tests/helpers/harness.ts`.

## Goal

The booking engine understands the four scheduling modes (`flex`, `slot`, `day`, `project`) end to end on the server, using the new catalog, with correct money, availability, holds, payments, emails, reminders, completion and reports. The existing `flex` behaviour must not regress.

## Bar

Match or beat Calendly's availability correctness for fixed-time events: a session is offered if and only if it can really be booked, can never be double booked even under concurrent requests, and times stay correct across midnight in Lagos time (WAT, no DST).

## Files you own

`src/worker/services/availability.ts`, `services/bookings.ts`, `services/emails.ts` (only `when`, `details`, `money`, and the booking email templates, not new file-delivery templates which another builder appends), `services/admin.ts` (reports and dashboard overview), `repositories/bookings.ts`, `routes/booking.ts`, `routes/public.ts`, `lib/time.ts`, `src/client/lib/format.ts` (overnight formatters only), tests under `tests/` for all of this. Another builder is adding portal file code in new files and `routes/account.ts` and `routes/admin.ts` additions and `index.ts` at the same time: never overwrite a whole existing file with Write, use Edit, and do not touch their new files. A third builder is changing client brand files. Ignore type errors that appear in files you do not own, they are mid-edit, and rerun later.

## Must do

1. **Time formatting is overnight safe.** `label12`, `hhmm`, `t12`, `hm` (server `lib/time.ts` and client `lib/format.ts`) treat minutes above 1439 as the next day (`1740` is `5:00am`). Add `endsNextDay(end)` and a range formatter that renders `11:00pm to 5:00am (Sunday)` style text where the weekday name is the day after `date`. `when(b)` in emails uses it.
2. **Session windows.** `availabilityService` loads `session_slots`. Pure, unit-tested function(s) compute windows for a date and kind: active rows where `weekday IS NULL OR weekday = weekday(date)`, ordered by start. A window is `available` when there is no clash in the package's room (existing `CLASH` rules including the buffer, holds, requests and blocks), it is not in the past, `minNotice` from `rules` is respected (use the window start, with overnight windows measured from the booking date), and the date is inside `bookAhead`.
3. **`GET /availability/day?date&package`** and **`/availability/month?month&package`** as described in ARCHITECTURE.md. Keep `duration`+`room` working for `flex` and for admin pickers. `day` mode: one whole-day window from the earliest day-slot start to the latest day-slot end of that weekday; available only if the room is free for all of it. `project`: `mode: "project"`, `slots: []`, every future day `available` in month view or simply no calendar needed (document your choice in the response). Month statuses: `closed` for days with no matching window, `full` when none are free, `limited` when one is left (and more than one exists), otherwise `available`.
4. **`priceDraft`**: resolve the package's mode. `slot`: `start` must equal the start of an active window of the package's `slot_kind` for that date's weekday (otherwise 400 "Pick one of the open sessions."); `end` and duration come from the window, `extraHours` must be 0; price is `package.price_kobo` flat. `day`: `start` must equal the day window start; duration is the whole window; no extra hours. `project`: date forced to the studio's today, `start = 0`, duration 0, no room (`roomId` ''), `people` not constrained by a room (1 to 200 accepted, default 1), no opening-hours or notice checks. `flex`: unchanged. Packages with `service_slug` must match the chosen service slug (when non-empty), keeping the existing category check. Extras: allowed when `(!e.category || e.category === svc.category) && (!e.service_slug || e.service_slug === svc.slug)`; an extra with `pricing = 'quote'` is listed with `price: 0, quote: true` and adds nothing to the total. Quote-priced packages still refuse to be booked. Add `scheduling`, `slotKind`, `slotLabel`, `unit`, `turnaroundDays`, `revisionLimit`, `dueDate`, `tracks` to `Draft`. Show `compareAtKobo` in the catalog response only (price charged is always `price_kobo`).
5. **Holds and bookings.** `createHold` uses the right window per mode and keeps all clash guarantees (it must stay a single atomic insert-if-free). `project` holds use a NULL room and never clash. `bookFromHold`, `submitRequest`, `createManual` carry every new column into `bookings` (`scheduling`, `slot_kind`, `slot_label`, `due_date`, `revision_limit`; extend `NewBooking`, `COLS`, `values`). `due_date` per ARCHITECTURE.md. Manual staff bookings (`createManual`) support all modes; for `flex` they keep `ignoreHours`. Approval requests (`day` mode, EP and album) hold the whole day until the request expires, exactly as requests do today.
6. **Reschedule, client change requests and moves.** `reschedule`, `requestChange` and `decideRequest` validate against the booking's mode: `slot` bookings can only move to an active window of the same `slot_kind` that is free; `day` to any free whole day; `project` bookings cannot be rescheduled (400 with a clear message). Keep the 48 hour free-reschedule policy and existing refund maths.
7. **Housekeeping.** `markCompleted` completes a `slot` or `flex` or `day` booking only after its end time has passed, overnight aware (a Saturday 11pm to 5am booking is not completed at midnight), and never completes `project` bookings. Reminders skip `project` bookings. Holds for `project` expire like any other.
8. **Calendar and dashboard.** `calendar()` and the overview's "today" list exclude `project` bookings (they have no time). The calendar response must still carry overnight bookings with their real `end` (above 1440) so the UI can draw them. Add `projects: n` (confirmed project orders with `delivered_final_at` NULL) to the overview payload for a "Remote orders" stat.
9. **Reports.** Group blank `room_name` as "Remote orders". `utilisation` minutes still use `end_min - start_min` (projects contribute zero). CSV shows blank start and end for projects and `endsNextDay`-aware times for overnight sessions.
10. **Emails** (`details`, `when`): sessions show `Room`, `Date`, and the time range (overnight aware). Projects show `Order placed`, `Delivery due` (when `due_date` set) and no room or time lines. The confirmation email for a project says what to do next: upload your files in your portal (link), and that finished work is delivered there. Booking confirmation and payment emails for everything keep working.
11. **Catalog endpoint** adds `sessions` and returns the new package/extra columns. Packages in a non-bookable category stay hidden from the public catalog as today. Services with no bookable packages stay listed.
12. **Tests.** Unit tests for the pure window functions and formatters (including overnight, the adjacency of Session 1 to 2, a Sunday night request being closed, minNotice for the night window). API integration tests in `tests/api/booking.test.ts` using the harness covering, per mode: availability, a hold that conflicts with a second hold, payment through the demo provider into a confirmed booking with the right columns, an invalid start rejected, a past date rejected, extras (fixed and quote), deposit versus full for `full-production`, the EP request-then-approve-then-pay path, a project order (no room, due date), reschedule per mode, housekeeping completing an overnight booking only after it ends (use fake timers or set rows directly), the two production bookings surviving the migration (run a test that loads `prod`-like rows if practical, otherwise keep the manual rehearsal in your report). Existing tests stay green.
13. **Production data rehearsal.** `bash <scratchpad>/harness/dev.sh <port> prod-rehearsal prod` starts an instance on a copy of live data. Confirm the two existing bookings still list in `/api/admin/bookings`, open in `/api/admin/bookings/:id` and show in the client's account overview. Stop the instance.

## Out of scope

Any client UI, anything about files and revisions, policies and copy (already in the migration), brand.

## How it will be judged

A fresh critic runs `npm test`, starts its own instance, and tries to break availability and booking with curl or Playwright-free API calls: double bookings via concurrent holds, invalid starts, the Saturday night window on a Sunday, minNotice, overnight formatting in emails (read the outbox), money (deposit rounding, extras), completion at midnight, project orders hold and pay, EP request flow, and regressions on flex packages (podcast, stage, photo packages stay bookable by staff). Plus a compliance pass against BRIEF.md R6 to R16 on the catalog data.
