# P3. Portal files, deliveries and revisions (server)

Read first: `.gauntlet/BRIEF.md`, `.gauntlet/ARCHITECTURE.md` (the "Portal files" and "API contract" sections are your contract, follow the shapes exactly because a UI builder will code against them), then the existing code: `routes/account.ts`, `routes/admin.ts` (the `/uploads` image route shows the R2 pattern), `site.ts` (`media`), `services/notifications.ts`, `services/emails.ts`, `middleware/auth.ts`, `shared/permissions.ts`, `tests/helpers/harness.ts`.

## Goal

Everything finished goes through the portal. Staff upload work to a booking and deliver it in one action; the artist is notified once and downloads it from their own portal; payment gates the download; the artist can upload their own files for staff to download; mixing and mastering style revisions are limited and auditable; nothing can be read by the wrong person. All of it backed by R2 multipart uploads through the Worker (no new services, no new dependencies).

## Bar

Match or beat Fiverr's order delivery rules (deliver, request a limited number of revisions, approve to complete, nothing changes after completion) and the access safety of a private Dropbox or WeTransfer link: nobody can fetch a file they are not entitled to by any id, and a locked file stays locked by every route.

## Must do

1. **Upload protocol** exactly as in ARCHITECTURE.md: begin (validates booking access, extension allowlist, `size` between 1 byte and 1 GiB, booking state, R2 binding present, else a friendly 400/503) creates the row and an R2 multipart upload; `PUT parts/:n` takes the raw body (at most 8 MiB, parts must be numbered from 1, a re-sent part replaces the old one, record `{partNumber, etag}` in the row); `complete` verifies every part up to the highest is present, completes the multipart upload, stores the real size from R2 (not the declared one), refuses a size mismatch beyond tolerance, sets `state = ready` and `completed_at`; `DELETE` aborts or removes (soft delete `state = removed`, and delete the R2 object). Calling complete twice is safe. Keys are `portal/<booking_id>/<file_id>`. Never put user text in a key.
2. **Who may do what**, enforced in the service not only the route: client owns the booking (`user_id`), direction `upload`, booking not cancelled or rejected; staff need `deliver_files` for every file route, direction `delivery` for staff uploads. A client cannot touch deliveries other than listing and downloading permitted ones. Staff cannot upload as clients. Unknown or foreign ids always return 404, never 403 (do not leak existence).
3. **Gate and download.** `GET .../download` streams from R2 with `Range` support (206 and `Content-Range`), `ETag`, `Accept-Ranges: bytes`, `Content-Length`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`, `Content-Disposition` built safely (RFC 5987 `filename*` plus an ASCII fallback, no raw quotes or newlines), attachment by default and inline only for `?inline=1` on audio types. The gate in ARCHITECTURE.md rule 2 applies to the file, to inline streaming and to range requests. Keep a pure function `canDownload({...})` that is unit tested. Count downloads, set `first_downloaded_at`, and write an audit log row for every download by anyone ("Downloaded delivery" with ref, file title and who).
4. **Deliver.** `POST /admin/bookings/:id/deliver`: all `fileIds` must be staged deliveries of that booking in state `ready`. Sets `title` per item, `note`, `delivered_at`, `version` (next version per title), `released` when requested. If an open revision request exists and `resolvesRevision` is not false, mark it done. If `final` is true: set `delivered_final_at`, status `completed` (only when the booking is `confirmed` or `completed`; never for pending, approved, cancelled or rejected), and close revisions. One notification per call: email to the client (never an attachment; subject like `Your music is ready · <ref>`; body lists titles, says the files are in the portal with the link, and if a balance is due says the files unlock when it is paid and includes the pay link; for a booking with no account it explains how to create an account with that email), plus an in-app notification, plus an audit row. If the booking has no `user_id` and no email, the call still succeeds but the response says `{ notified: false, reason: "no_contact" }` so the UI can warn.
5. **Revisions.** `POST /account/bookings/:id/revisions` per rule 4; a note of 3 to 2000 characters is required; increments `revisions_used` and creates the request in one atomic batch (two simultaneous requests must not exceed the limit: use a conditional `UPDATE ... WHERE revisions_used < revision_limit` and check `changes`). Notifies staff holding `deliver_files` (no client email or phone in the text). `POST /account/bookings/:id/approve` and staff `POST /admin/bookings/:id/finalize` finalize. After finalization: no revision, no new delivery, no client upload changes that matter (uploads still allowed to the booking? no: reject with a clear message), refunds and cancellation stay impossible because the booking is `completed`.
6. **Portal views** per the API contract: `GET /account/files`, extend `GET /account/bookings/:id` (compose in the route), `GET /admin/bookings/:id/files`, and the production queue `GET /admin/deliveries?tab=` with the four tabs defined as: `todo` (status `confirmed`, not final, no published delivery yet, and either scheduling `project` or a `due_date` set), `revisions` (has an open revision request), `client` (client uploads exist that staff have not downloaded yet, track with `first_downloaded_at` NULL on any `upload` row), `delivered` (has a published delivery). Rows carry the fields listed in ARCHITECTURE.md plus `overdue` (due_date before the studio's today and not final) and sort by due date then age. Needs `deliver_files`; the rows must not carry client email or phone.
7. **Notifications for staff.** When a client confirms an upload batch (`POST /bookings/:id/files/notify`, which accepts only that booking's own `ready` upload ids and ignores the rest), `notifyStaff(env, "deliver_files", ...)` once with ref, artist name, package and file count and a link to `/admin/deliveries`. Revision requests notify the same way. Nothing sent to `deliver_files` holders contains client contacts. Rate limit the notify route per booking to once per 2 minutes.
8. **Walk-in clients.** `PUT /admin/bookings/:id/details` accepts an optional `contact_email`; when given it validates, updates the booking, links `user_id` to an existing verified client with that email, and audits it. Needs `update_booking_details`.
9. **Housekeeping** in `filesService.housekeeping(env)` called from the cron in `index.ts`: abort and mark `removed` any file stuck in `uploading` for over 24 hours (abort the multipart upload, ignore errors), and delete R2 objects of `removed` rows older than 7 days. Staged deliveries that were never published are left alone.
10. **Hostile input.** Filenames with quotes, newlines, `../`, unicode and 500 characters; content types that lie; zero byte files; parts out of order; completing early; completing someone else's upload; one client probing another's booking and file ids (both existing and non-existing must look identical); a producer trying to read contacts; a client trying to download an undelivered or locked file by every route including inline and range; huge `size` declared; a cancelled booking trying to upload; replaying the same part number; two parallel complete calls. All covered by tests or consciously refused.
11. **Docs.** Add `docs/PORTAL.md` for the studio team and developers: how delivery works end to end, the payment gate and the release switch, revisions, the producer role, limits, storage costs on R2 (10 GB free, then $0.015 per GB-month, no egress fees) and how to clear space. Keep it plain and short.

## Out of scope

All client and admin UI, the catalog, scheduling, policies text, brand.

## How it will be judged

A fresh critic runs your tests, then attacks through the harness and a live instance: two client accounts, a producer, a front desk user, the CEO. Large file (30 MB or more) multipart upload and ranged download byte for byte (compare sha256), locked and released flows, revision limit race, finalization rules, notification contents (read the outbox for contact leaks), filename header safety, existence leaks, quotas, abort and cleanup. Plus a workflow pass against the Fiverr bar.
